# 구형 XP 프로그램 정적 분석 지도

이 문서는 `sinbee_n.exe`를 다시 처음부터 분석하지 않도록 만든 전체 프로그램 색인이다.
XP의 동작을 참고하되 **XP가 업무상 정답이라고 단정하지 않는다.** 실제 장부와 사용자 확인이
우선이며, 실행 파일에서 확인되지 않은 부분은 반드시 `미확정`으로 취급한다.

## 원본과 분석 범위

- 원본: `sinbee_n.exe`, VB6 네이티브 실행 파일, 1,568,768바이트
- 원본 SHA-256: `ffc5cda8adf9ec1311d8321d96362db4111369760f9804e79f31c2a86f16e11d`
- 원본 수정 시각: 2004-03-05
- 정적 분석만 수행했으며 EXE는 실행하지 않았다.
- Ghidra 12.1.3 자동 분석 결과: 함수 487개, 정의 문자열 1,180개, 심볼 15,250개
- 정산 관련 대형 함수 14개와 보조함수 6개를 별도로 디컴파일했다. 월정산 본체
  `004f0970`은 기본 120초 분석은 시간 초과됐지만 제한을 늘린 재분석에서 전체 C 유사코드
  추출에 성공했다. 다만 VB6 Variant와 화면 배열의 원래 변수명은 소실되어 분기 의미를
  화면 필드·SQL·호출 함수와 교차 확인해야 한다.

이 숫자는 Ghidra가 인식한 항목 수다. VB6 런타임 보조 코드와 실제 업무 이벤트가 섞여 있으므로
`487개 함수 = 487개 업무 기능`이라는 뜻은 아니다.

## 근거 등급

1. 실제 업무 사례와 장부를 사용자가 확인한 결과
2. 현재 DB 원자료를 독립적으로 재계산한 결과
3. 여러 XP 출력물에서 반복 확인된 결과
4. EXE의 SQL 문자열과 해당 코드 참조
5. EXE의 폼/컨트롤 이름 또는 단일 출력물
6. 필드 이름과 일부 기계어만으로 한 추정

수정할 때 4~6등급 근거만 있으면 코드를 확정하지 말고 `미확정`으로 남긴다.

## 수금 구조

XP의 수금 등록 SQL은 다음 필드를 한 행에 함께 저장한다.

`sukum_char`, `sukum_gb`, `su_sil_amt`, `su_dache_amt`, `s_method`, `manage_desc`

정적으로 확정된 흐름은 다음과 같다.

- 월세 집계는 `sukum_char='01'`만 대상으로 `su_sil_amt`와 `su_dache_amt`를 따로 합산한다.
- 월정산 본체는 `sukum_char='06'`도 별도 조회한다.
- 퇴실정산 납부내역 표는 `sukum_gb <> '02'`이고 `sukum_char <> '06'`인 행만 보여준다.
- 퇴실 확정 시 종류 `06`인 수금 행을 만들며, 퇴실 취소 시 같은 종류의 행을 삭제한다.
- 따라서 `실입금`, `대체`, `퇴실정산 조정`은 서로 다른 의미다. 하나의 입금액으로 합쳐
  판단하면 XP 흐름과 달라진다.

코드값의 한글 명칭은 DB의 `gicho_code`와 실제 화면을 함께 확인해야 한다. 문자열만 보고
종류 `06`의 업무 명칭을 임의로 확정하지 않는다.

## 퇴실정산 저장 흐름

`004a9640`에서 확인된 순서는 다음과 같다.

1. 대상이 현재 입주(`ipju_gb='A'`)인지 확인한다.
2. `bd03_det`를 `out_jungsan_end='Y'`, `ipju_gb='B'`, `out_dt`, `out_seq`,
   `plan_out_dt` 등으로 갱신한다.
3. 같은 호실의 다른 입주 이력과 호실 상태를 확인하고 `bd03_m.rent_gb='B'`로 바꾼다.
4. `bd07_out`에 계산 결과와 당시 계약정보를 함께 저장한다.
5. `sukum01`에 `sukum_char='06'`인 정산 조정 행을 저장한다.

`bd07_out`에 직접 확인된 값:

- 기준일, 입주 개월/일수
- 수금총액
- 수리·전기·선급·시설·가스·기타·정산금액
- 선/후불과 입주일·성명·주민번호·연락처
- 보증금·예치금·임대료·관리비 스냅샷

취소 함수 `004b55f0`와 `00502980`은 입주상태를 되돌리고 `plan_out_dt`를 비우며,
`bd07_out`과 종류06 수금행을 삭제한다. 웹도 이 세 영역을 한 작업 단위로 맞춰야 한다.

## 월정산 대상 선정과 집계

월정산 본체 `004f0970`의 SQL에서 다음은 확정된다.

- 입주 이력 대상은 현재/예정 상태 `ipju_gb in ('A','C')`와, 이미 퇴실했지만 정산월에
  걸쳐 있는 `ipju_gb='B' and out_dt >= 기준`을 함께 포함한다.
- 입주자가 없는 호실도 `bd03_m.rent_gb='B' and del_yn='N'` 조건으로 합집합한다.
- 호실별 월세 수금은 정산월 범위, `sukum_char='01'`, `del_yn='N'` 조건으로
  `sum(su_sil_amt)`와 `sum(su_dache_amt)`를 분리 집계한다.
- 종류06 행과 그 `manage_desc`를 별도로 조회해 퇴실 조정을 반영한다.
- 저장 시 `jungsan_det`에는 계약금액, 미수, 관리지시, `dache_gb`가 함께 들어간다.

이 구조 때문에 퇴실월 계산을 `napbu_gb` 하나만 보고 일할 계산하면 부족하다. XP도 정산월의
실입금, 대체금, 종류06 퇴실 조정행을 함께 읽는다.

### XP 누적 미수 계산의 실제 흐름

보조함수까지 연결하면 XP 월정산 본체가 화면에 놓는 누적 미수는 다음 흐름이다.

1. `00494e30`: 입주일과 기준일 사이 월 경계를 세어 `(임대료 + 관리비) × 청구개월수`
2. `004949a0`: 기준일까지 입주자 부담 수리비 누계
3. `00495360`: 기준일까지 해당 입주자의 `su_sil_amt` 누계
4. 본체: `누적 청구액 + 입주자 부담 수리비 - 누적 실입금`

디컴파일된 본체의 산술은 실제로 `local_40 + 수리비누계 - 실입금누계` 순서다.

중요한 차이: `00495360` SQL에는 `sukum_char` 조건이 없다. 즉 XP는 이 누적 실입금 단계에서
수금 종류를 가리지 않고 `su_sil_amt`를 합친다. 보증금·예치금 실입금이 같은 입주자의
`sukum01`에 들어 있으면 월세 미수에서도 차감될 수 있다. 이는 XP의 실제 동작이지만 현재
업무 규칙으로 그대로 복제해야 한다는 뜻은 아니다. 웹에서 보증금/예치금을 월세 수금총액과
분리하기로 한 결정은 이 오래된 혼합 계산을 의도적으로 바로잡는 변경이다.

### 아직 수식까지 확정되지 않은 부분

`004f0970` 전체 디컴파일에는 성공했지만 화면 셀 번호와 Variant 임시변수의 원래 이름이
사라져 있다. 다음 조합의 정확한 분기와 원 단위 절삭 시점은 실제 사례와 대조 전까지
확정하지 않는다.

- 계약은 후불이지만 실제로 선입금한 입주자
- 선불 입주자의 퇴실월 실입금 완료/미입금 차이
- 선불 입주자에게 임대료 대체를 한 경우와 하지 않은 경우
- 종류06 퇴실 조정과 당월 월세 실입금/대체금이 동시에 있는 경우

이 항목은 `napbu_gb`만으로 추측하지 말고, 동일 사례의 XP 출력 또는 DB의 종류06 행을 확보해
검증한다. 현재 웹의 `_jungsan_out_settle_amt()`는 이 모든 조합이 검증된 XP 복제본이 아니다.

## 월정산 인쇄 흐름

`004e56c0`은 월정산 본문 외에 다음을 별도로 조회한다.

- `bd05_suri`: 기간 내 집주인 부담액이 0보다 큰 수리
- `sJungke01`: 기간 내 중개수수료

확보된 XP PDF와 함께 확인한 배치는 다음과 같다.

- 제목 약 22pt, 표 약 9pt, 본문 약 10pt
- 당월지급액과 금액은 첫 행
- 임대료대체는 첫 행, 보증금대체는 세 번째 행
- 수리비 상세 다음 중개수수료 상세은 한 행 띄워 구분
- 수리비가 없어도 중개수수료 앞에 의도된 구분 여백은 하나만 둔다.

수식은 맞지만, EXE 전체 흐름을 확인한 지금은 `후불이면 항상 +`, `선불이면 항상 -`만으로
일반화할 수 없다. 실제 실입금과 종류06 정산행을 읽어 판단하도록 다시 설계하기 전에는
예외 조합을 검증 완료라고 표시하면 안 된다.

### 웹 보정 결정: 달력 말일과 기존 종류06 우선

- 납부기준일이 29·30·31일인데 해당 월에 그 날짜가 없으면 그 달의 마지막 날로 본다.
- 1월 31일 기준은 평년 2월 28일, 윤년 2월 29일, 4월 30일로 순환한다.
- 과거 XP 퇴실자료는 `sukum_char='06'`에 월말정산서용 양수·음수·0 조정액이 이미 저장돼
  있으므로 웹에서 선후불만 보고 다시 계산하지 않고 그 값을 우선한다.
- 종류06이 없는 웹 신규자료에만 달력 기반 예비 계산을 사용하며, 실제 입금·대체 조합이
  완전히 검증되기 전까지 이를 XP 확정식이라고 부르지 않는다.

### 계약금액 변경이력

XP와 기존 웹은 `bd03_det`의 최종 금액을 덮어써 과거 인상·인하 시점을 잃었다. 웹은
`bd03_terms_hist`에 입주자별 적용일, 보증금·예치금·월세·관리비·선후불과 변경내용을 보존한다.

- 신규 입주는 입주일 조건을 최초 이력으로 기록한다.
- 기존 입주자의 계약금액을 수정하면 이전 조건을 입주일부터 보존하고 새 조건은 수정 저장일
  기준으로 기록한다.
- 퇴실정산 거주기간 총액은 각 변경기간과 실제 임대주기 일수로 나눠 계산한다.
- 이미 과거에 덮어써서 사라진 변경내용은 수금액만 보고 임의 복원하지 않는다.
- 과거 변경을 뒤늦게 입력해야 하는 경우를 위한 별도 적용일 입력 화면은 아직 없다.

정산 코드를 고치기 전 최소 확인 순서:

1. 이 문서에서 해당 XP 함수·테이블·코드값을 찾는다.
2. `docs/xp-settlement-logic.md`의 확정/미확정 규칙을 확인한다.
3. 현재 DB에서 실입금·대체·종류06을 분리 조회한다.
4. XP 출력 또는 사용자가 확인한 실제 장부와 결과를 비교한다.
5. 검증되지 않은 조합을 일반화하지 않는다.

## 분석의 한계

- VB6 네이티브 코드는 변수명과 원본 이벤트명이 대부분 사라져 있다.
- EXE 안의 SQL은 확실한 증거지만, 동적으로 이어 붙인 값의 업무 의미는 주변 코드 확인이 필요하다.
- 프로그램 원본 소스와 당시 DB가 없으므로 모든 분기를 100% 복원했다고 말할 수 없다.
- XP 자체 계산도 오래된 업무 규칙이나 오류를 포함할 수 있다.

따라서 이 문서는 `XP를 그대로 믿는 명세서`가 아니라, 다음 작업자가 맨땅에서 다시 시작하지
않게 하는 **증거 지도**다.
